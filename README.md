# .github

Единые правила разработки и шаблоны для репозиториев `Abrikosov-group`.

## Организационное ИИ-ревью

Центральный reusable workflow `.github/workflows/review-all.yml` выполняет
двойное ревью pull request:

- GPT-5.3-Codex-Spark с усилием `xhigh` через Codex CLI на отдельном защищённом
  self-hosted runner и оплаченный вход ChatGPT;
- Claude Sonnet 5 с усилием `xhigh` через подписочный OAuth Claude Code на
  отдельном защищённом self-hosted runner.

Gemini и платные API-ключи моделей не используются.

Codex запускается командой `codex exec --model gpt-5.3-codex-spark` с
`model_reasoning_effort="xhigh"`. Workflow не вызывает `@codex review`, не
использует квоту встроенного Security Review и не требует OpenAI API-ключ.
Полный текстовый diff передаётся модели без checkout недоверенного PR на сервере.
Сырые Git binary patch, base64/base85 payload и содержимое известных binary-типов
не передаются: вместо них модель получает точный JSON-manifest
с путями, режимами, blob ID, размерами, SHA-256 файлов и
`binaryManifestSha256` полного списка. Оба ревью явно публикуют число и полный список
непроверенных binary paths. Результат проходит строгую проверку перед публикацией.

Подключатель обязан передать одну ограниченную runner group и три разных label:
для служебной оркестрации, Codex и Claude. Все jobs выбирают runner одновременно
по group и label и проверяют его точное имя до содержательной работы. Модельные
runner изолированы друг от друга и от служебного runner. На Codex runner должен
быть выполнен подписочный вход `codex login`; его `CODEX_HOME` сохраняется между
запусками. Окончательный prompt одного запуска Codex ограничен 512 KiB. Поэтому
бинарно-тяжёлые PR больше не блокируются только из-за base85-представления файлов,
а действительно большой текстовый diff по-прежнему требует отдельного решения.

Репозитории подключают workflow маленьким файлом
`.github/workflows/review-all.yml`. Для нового репозитория используйте
организационный шаблон **«Двойное ИИ-ревью Codex и Claude»** во вкладке
**Actions → New workflow**.

Сам центральный репозиторий `.github` использует такой же слушатель в файле
`.github/workflows/review-all-trigger.yml`, поэтому команда работает и в его PR.

Шаблон вызывает центральный workflow по полному commit SHA. Обновление версии
в подключённых репозиториях выполняется отдельным проверяемым изменением.
Сначала объединяется новая версия reusable workflow, затем отдельный pin-PR
одновременно обновляет `uses` и `trusted_workflow_sha` на exact merged SHA. До этого
старые callers продолжают вызывать предыдущую совместимую версию.

Двойное ревью запускается автоматически:

- при открытии PR сразу в состоянии **Ready for review**;
- при переводе PR из Draft в **Ready for review**;
- после каждого нового коммита в готовом PR;
- при повторном открытии готового PR;
- при фактической смене целевой base-ветки без изменения Head SHA.

Изменения только заголовка или описания PR не запускают модели повторно.

На уровне подключателя автоматические события одного Head могут отменять свои
дубликаты, но concurrency-ключ включает Head SHA: старое событие не отменяет
вызов нового снимка. Центральный движок объединяет ручные и автоматические
запуски одного PR в общую очередь без отмены активного запуска. Одновременно
выполняется одно ревью, до 100 следующих запусков могут ожидать своей очереди.

Каждый получивший право на выполнение запуск заново получает текущий Head через
GitHub API, даже если исходное событие относилось к старому SHA. Перед анализом
и публикацией workflow повторно сверяет текущий Head, поэтому устаревший
результат не публикуется и не перезаписывает статус нового снимка. Для точного
Base/Head и модели результат публикуется только один раз.

Все центральные этапы ограничены `timeout-minutes`: подготовка Codex — 10 минут,
анализ Codex и Claude — по 25 минут, публикация — по 7 минут. GitHub не разрешает
`timeout-minutes` в вызывающем job с `uses`, поэтому ограничение задаётся внутри
reusable workflow.

Для совместимости со старыми подключателями центральный workflow принимает
`REVIEW_DISPATCH_TOKEN` как необязательный секрет, но не читает и не использует
его. Новые подключатели этот секрет не передают.

Для ручного повторного запуска добавьте в комментарий готового PR:

```text
/review-all
```

`/review-all` повторно запускает Codex и Claude. Для повторного запуска только
Claude используйте отдельный комментарий:

```text
/review-claude
```

Если manifest содержит binary paths, успешный итог дополнительно требует disposition
для exact Head SHA. Автор PR либо участник с текущим `write`, `maintain` или `admin`
публикует отдельный комментарий без Markdown fence; порядок файлов должен совпадать
с manifest:

```text
/binary-disposition
{"schemaVersion":1,"headSha":"<40-символьный Head SHA>","binaryManifestSha256":"<SHA-256 из ревью>","files":[{"path":"assets/font.woff2","decision":"manual-review","justification":"Файл открыт вручную; начертание и таблицы символов проверены."}]}
```

Для каждого файла разрешены решения `manual-review`, `automated-check` (с полем
`runUrl` успешного GitHub Actions run exact Head), `not-required` и `accepted-risk`.
Последнее решение может публиковать только `Etogerman` с ожидаемым stable GitHub ID.
Пустое обоснование, чужой actor, неполный список, старый Head или другой manifest дают
`C42.1`. Новый корректный комментарий пересчитывает coverage без повторного расхода
квоты моделей, если оба exact ревью уже опубликованы.

После принятия ручной команды бот ставит на неё 👀. Эта реакция остаётся, пока
запуск ожидает общей очереди. Когда центральный workflow действительно начинает
ревью, 👀 заменяется на 🚀 и появляется статусный комментарий. Если запуск не
дошёл до этой стадии, бот по возможности заменяет 👀 на 😕. При принудительной
остановке всего запуска GitHub очистка реакций выполняется в режиме best effort.

Для ручного и автоматического запуска бот создаёт один статусный комментарий в
PR: сначала он показывает запуск обоих ревьюеров, затем обновляется итогом
каждого из них и ссылкой на журнал Actions. При следующем коммите обновляется тот
же комментарий.
