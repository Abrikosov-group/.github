# Третий независимый ревьюер DeepSeek

Общий контроллер `.github/review/run-deepseek-review.mjs` обслуживает C2 (ТЗ) и C3
(PR). Он закреплён на `deepseek-flash`, `thinking.type=enabled`,
`reasoning_effort=max`. Профиль принят владельцем 20 сентября 2026 (МСК).
Успешный ответ подтверждает возвращённую модель и принятие параметров запроса.
Когда API не возвращает effort, запись содержит `effortEcho: null`: внутреннее
усилие провайдера отдельно не подтверждено.

Запрос явно задаёт `max_tokens: 131072`: это штатный предел API для режима
`max`, общий для рассуждений и ответа. Неполный ответ не публикуется;
его безопасные метаданные (причина остановки, расход токенов, ID ответа)
сохраняются без текста рассуждений и частичного отчёта. Автоматического повтора нет.

## C3 — общий workflow

После выпуска проверенного SHA инфраструктуры каждый разрешённый caller передаёт:

```yaml
with:
  # uses и trusted_workflow_sha должны указывать на один проверенный полный SHA.
  deepseek_enabled: true
secrets:
  DEEPSEEK_API_KEY: ${{ secrets.DEEPSEEK_API_KEY }}
```

Это дополнение к существующим параметрам и секретам caller, не полный workflow.
По умолчанию роль выключена; добавление нового секрета и включение в проекте —
отдельное действие в разрешённых владельцем границах. Автоматического изменения
настроек GitHub или runner group контроллер не выполняет.

DeepSeek получает тот же `prompt.txt`, diff, binary manifest и JSON-схему, что
Codex. Подготовка сохраняет этот вход и при повторном использовании отчёта Codex.
Запрос без инструментов выполняется в отдельном GitHub-hosted job; запускается
только код доверенного полного SHA инфраструктуры. Подписочные CLI, их защищённые
runner и один утверждённый резерв Codex сохраняются. `/review-claude` третью роль
не запускает.

Анализ имеет `pull-requests: read`, отдельная публикация — `pull-requests: write`.
API-ключ доступен только шагу анализа. Публикация проверяет сохранённые хеши,
профиль, фактическую модель, форму отчёта, строки diff и актуальные Base/Head.
Результат имеет отдельный маркер `deepseek-review-max-v1`; отчёт другого усилия
или модели не переиспользуется. Повтор автоматического события использует уже
опубликованный отчёт точного снимка; явная ручная команда начинает новый раунд.

Публикации основной пары не ждут DeepSeek, а DeepSeek — их завершения. Итоговый
комментарий основной пары прямо указывает, что его счётчик относится к паре.
Отдельный отчёт DeepSeek и job summary доступны в том же запуске workflow.
Отсутствующий отчёт третьей роли не добавляет обязательный merge gate: эти jobs
не следует назначать обязательными проверками защиты ветки. Ошибка, неполный
ответ или отсутствие ключа фиксируются как `unavailable`, а не как пустое ревью.

При смене снимка отчёт сохраняется с `snapshot_no_longer_current`; при ошибке
повторной проверки GitHub — с `freshness_unconfirmed`. Такой отчёт не публикуется
как актуальный. Артефакт `deepseek-review-output-<run_id>-<run_attempt>` хранится
30 дней, в том числе при позднем результате. Ответственный за задачу переносит
содержательный результат и его разбор в постоянное досье и доставляет его по
действующему workflow. Артефакт CI сам по себе не заменяет этот разбор.

## C2 — общий локальный контроллер

Контроллер C2 передаёт ту же исходную задачу и allowlist файлов неизменяемого
снимка, которые получили обязательные ревьюеры. Manifest — JSON-объект
`{"относительный/путь": "sha256"}`. В allowlist входят ТЗ, исходный запрос,
решения владельца, правила и исходники; чужие отчёты, авторская переписка и
секреты исключаются составителем пакета. Manifest и выбор задачи доверенные:
их формирует контроллер, а не проверяемый PR.

```sh
node .github/review/run-deepseek-review.mjs \
  --kind c2 --input /path/to/frozen/input \
  --manifest /path/to/snapshot-manifest.json \
  --task review-task.md --output /path/to/new/deepseek-attempt
```

Ключ поступает через `DEEPSEEK_API_KEY`. В разрешённой macOS-среде флаг
`--keychain` читает только service `com.abrikosov.deepseek.reviews`, account
`api-key-20260920` через стабильный локальный клиент `DeepSeekReviewCredential`;
значение используется в памяти и не передаётся в аргументах. Клиент устанавливается
из `deepseek-keychain-client.c` в приватный каталог владельца
`~/Library/Application Support/Abrikosov/Review Credentials/` (0700), бинарный файл
имеет права0500 и локальную подпись. В обычном запуске UI запрещён средствами
Keychain; отсутствие доступа даёт один `credential_unavailable`, без повторов.
Только заранее согласованная операция при присутствующем владельце использует
`--interactive-pipe` и сразу направляет прочитанный ключ в GitHub Secret через stdin.
Постоянное доверие подтверждается отдельным новым запуском с UI запрещённым;
нажатие «Разрешать всегда» само по себе не считается успешной проверкой.
Ключ не сохраняется в локальный файл. После блокировки Связки ключей, выхода из
системы или изменения подписи клиента доступ может потребовать восстановления.
Каталог результата создаётся эксклюзивно: тот же путь нельзя использовать для
незаметного второго запуска. Родительский каталог должен существовать.

Каждый запуск начинает свежую историю. Модель имеет только `list_files`,
`read_file`, `search_text` по allowlist; запрещены symlink, выход за корень и
изменившиеся хеши. Пути относительно `input/`, без этого префикса. Исходники не
исполняются. Бинарные данные не передаются, доступно только чтение текста.
Пределы: 20 минут, 48 обращений API в одном диалоге, до 16 инструментов в одном
ответе, 400 строк чтения, 128 KiB на результат инструмента и 2 MiB суммарных
результатов инструментов. Превышение даёт явный неполученный отчёт. Отдельного
повтора или замены модели нет. Служебное reasoning между tool calls сохраняется
только в памяти, согласно [контракту API](https://api-docs.deepseek.com/guides/thinking_mode/).

Результаты: `review.md` (C2) либо `review.json` (C3), `result.json` с фактическими
параметрами и чтениями, manifest и запись попытки. `completed` означает получение
валидного отчёта; допуск C2, полноту охвата и содержательную применимость проверяет
контроллер C2. DeepSeek не заменяет обязательную пару и не изменяет её счётчики,
ID запусков или принятые результаты.

## Разбор результатов

Первую находку разбирают при получении, пока другие роли заканчивают исходный
снимок. Совпадения связывают по причине и доказательству исправления; новые причины
расследуют. Подтверждённый P0/P1 реализации требует расследования, сохранённого
отчёта и отдельного ТЗ через C2 до исправления. Дефект самого ТЗ остаётся в C2.
Поздний отчёт относится к своему снимку; успешный старый отчёт не подтверждает
изменённую версию. Решение о выпуске учитывает все полученные замечания.

Проверки инфраструктуры: `node --test .github/review/*.test.mjs` на Node.js 24.
