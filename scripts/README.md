# Изменение списка workflow общей группы раннеров

`runner-group-workflows.mjs` добавляет один workflow в уже существующую
организационную группу с `visibility=selected`. Скрипт запускается вручную
администратором через настроенный `gh`; он не является GitHub Actions job
и не хранит токены. Без `--apply` выполняются только чтения.
Учётная запись должна иметь право и на изменение группы, и на добавление
репозиториев в неё: эти операции используют разные REST endpoints.

```bash
node scripts/runner-group-workflows.mjs \
  --org Abrikosov-group \
  --group-id 3 \
  --add-workflow 'Abrikosov-group/Telegram_channel/.github/workflows/review-all.yml@refs/heads/staging' \
  --require-repo-id 1109363720 \
  --require-repo-id 1292854106
```

После проверки выведенного списка ID та же команда с `--apply` меняет группу.
Для других групп
укажите их ID, полный путь workflow и ID репозиториев, которые обязательно
должны иметь доступ. Скрипт работает только с группами, уже ограниченными
списком workflow. Изменение самого доступа репозиториев и удаление workflow
в его область не входят.

Причина защиты: 19.10.2026 обычный `PATCH` списка workflow группы № 3 с
`visibility=selected` обнулил её список репозиториев. Последующее
восстановление добавило только Telegram_channel, оставив Sawabook без Codex
runner на 25 ч 37 мин. [Журнал аудита](https://github.com/organizations/Abrikosov-group/settings/audit-log?q=action%3Aorg.runner_group_updated+created%3A2026-10-19..2026-10-20).

Скрипт перед записью читает **все** страницы текущего списка репозиториев,
проверяет обязательные ID и сохраняет список workflow. В `PATCH` передаёт
только обязательное имя группы и настройки списка workflow, не повторяя
неизменённую `visibility`; флаг доступа публичных репозиториев сохраняет.
Сразу после записи он сверяет доступ и возвращает
каждый пропавший ID отдельным добавляющим `PUT`, затем повторно проверяет
доступ и список workflow. Ошибка чтения, записи или проверки даёт ненулевой
код завершения; дальнейшее подключение проекта в таком случае останавливают.

Обновления одной группы выполняют последовательно. Скрипт предотвращает
длительную незамеченную потерю доступа, но API не делает изменение двух
настроек атомарным: между `PATCH` и восстановлением возможен краткий разрыв.
Перед первым применением на действующей группе проверьте поведение команды
на некритичной группе; сам факт успешных локальных тестов не подтверждает
поведение живого GitHub API.
