# Правила работы с pull request

Эти правила действуют для репозиториев организации `Abrikosov-group`, если в конкретном репозитории не опубликована более подробная локальная инструкция.

## Перед отправкой на ревью

1. Завершите разработку и собственную проверку изменений.
2. Убедитесь, что автоматические тесты и проверки CI прошли успешно.
3. Переведите pull request из состояния **Draft** в **Ready for review**.
4. Проверьте, что описание PR объясняет цель и основные изменения.

## Запуск ИИ-ревью

В репозиториях, где подключён общий workflow ревью, проверка двумя ревьюерами
запускается автоматически при открытии готового PR, при переводе PR в
**Ready for review**, при повторном открытии, после каждого нового коммита и
при фактической смене целевой base-ветки:

- Codex Spark или Sol по размеру полного входа, с усилием `xhigh`;
- Claude Sonnet 5 с усилием `xhigh`.

Для ручного повторного запуска добавьте в обсуждение PR отдельный комментарий:

```text
/review-all
```

Команда повторно запускает независимую проверку двумя ревьюерами.
После принятия команды на комментарии появляется 👀. Пока запуск ожидает общей
очереди, реакция не меняется. При фактическом начале ревью 👀 заменяется на 🚀,
а в PR создаётся статусный комментарий с отдельным состоянием
Codex и Claude. Если запуск не дошёл до начала ревью, бот по
возможности заменяет 👀 на 😕. После завершения статусный комментарий обновляется
итогом и ссылкой на журнал.

Codex выполняется на защищённом серверном runner через подписочный вход
ChatGPT, без OpenAI API-ключа и без встроенного GitHub Security Review.
Результаты обоих ревьюеров относятся к зафиксированным Base и Head SHA.
Перед запуском каждой модели и публикацией результата workflow повторно
проверяет, что PR остаётся открытым, находится в Ready и сохраняет точные
Base/Head. Закрытый или возвращённый в Draft PR завершается без поздней
публикации результата.

## После запуска

1. Дождитесь завершения проверок во вкладке **Checks** или **Actions**.
2. Прочитайте итоговые комментарии ревьюеров в PR.
3. Автор изменений самостоятельно проверяет замечания и исправляет подтверждённые проблемы.
4. После каждого нового коммита дождитесь нового автоматического ревью актуальной версии кода.
5. Объединяйте PR с целевой веткой только после успешного CI и обработки существенных замечаний.

## Границы ответственности ИИ-ревьюеров

ИИ-ревьюеры:

- анализируют изменения и публикуют замечания;
- не изменяют код;
- не отправляют исправления;
- не объединяют и не закрывают PR.

Ответственность за проверку выводов ИИ, исправления и окончательное решение остаётся у автора PR и ответственного разработчика.

## Если команда не запустилась

Проверьте последовательно:

1. PR переведён в состояние **Ready for review**.
2. Для ручного повтора команда опубликована отдельным комментарием без дополнительного текста.
3. Во вкладке **Actions** появился запуск workflow ревью.
4. В репозитории установлен workflow `.github/workflows/review-all.yml`,
   вызывающий центральный workflow `Abrikosov-group/.github`.

Не публикуйте токены, ключи и значения GitHub Secrets в комментариях, коде или описании PR.


Для потребителя с явным `review_drafts: true` разрешён также открытый Draft во всех
проверках снимка. Его caller и server hook должны поддерживать тот же режим. Условия выше
для Ready остаются стандартом при `review_drafts: false`; включение у отдельного потребителя
не меняет запуск ревью PR этого организационного репозитория.

Автозапуск для PR, открытых App-ботами, включается отдельным входом
`trusted_automatic_bot_logins`: доверенный caller перечисляет точные логины через запятую,
и для них проверка `write` не выполняется; событие `pull_request_target` и head PR из того же
репозитория проверяются общим путём автозапуска для любого инициатора. Пустое значение сохраняет прежнее правило, а ручные команды по-прежнему доступны
только людям с фактическим `write`.


## Однократный резерв Codex

Доверенный caller может включить `codex_fallback_enabled: true`. Основная модель
остаётся GPT-5.3-Codex-Spark. Если CLI завершился без отчёта с подтверждённой
ошибкой доступности модели, явно указанным лимитом этой модели или технической ошибкой сервиса, в этом же раунде
один раз запускается GPT-5.6 Sol, `xhigh`, `service_tier=default` (обычная скорость).
Для Spark сохраняется прежний профиль без переопределения `service_tier`; запись
раунда обозначает отсутствие такого переопределения значением `null`. Для обеих
моделей сохраняется запасная локаль `LANG=C.UTF-8`, если окружение её не задаёт.
Завершённый по тайм-ауту процесс также допускает резерв; остановка пользователем,
смена Base/Head, общий сбой авторизации/квоты, слишком большой вход, невалидный
или содержательный отрицательный отчёт замены не вызывают. Claude продолжает
свою независимую проверку.

Каждая попытка получает отдельный ID и пустую рабочую папку; вход и схема остаются
теми же. Запись `codex-review-round-<run_id>-<run_attempt>` сохраняет снимок, хеш
входа, причину и зарезервированную попытку до запуска. Конкурирующий повтор
того же раунда останавливается; ошибка после резервирования не запускает ещё
один Sol. При GitHub rerun (`run_attempt > 1`) резерв отключён. Для нового раунда
применяется существующий штатный запуск ревью. Результат публикуется с фактической
выбранной моделью; поздний ответ Spark не заменяет принятый результат Sol.

Параметры в записи раунда — явно переданные CLI настройки; поддержка удалённым
runner и получение результата проверяются отдельным контрольным запуском после
подключения закреплённого SHA. Сам артефакт не доказывает успешного живого запуска.
Другие потребители сохраняют прежнее поведение, пока явно не включат параметр.

### Ротация аккаунтов Codex

На защищённом runner три независимых профиля находятся в
`/var/lib/sawabook-review-codex/profiles/{codex-1,codex-2,codex-3}`. Для одного
снимка контроллер использует слоты в фиксированном порядке:
`codex-1 Spark → codex-1 Sol → codex-2 Spark → codex-2 Sol → codex-3 Spark → codex-3 Sol`.
Переключение происходит только после подтверждённой технической ошибки, лимита
или недоступности текущего слота; успешный отчёт, отрицательное ревью,
неполный вход и общая недоступность квоты следующий профиль не запускают.
Каждая попытка получает отдельную рабочую папку и сохраняется в `round.json` вместе
с `profileId`, слотом, моделью, причиной перехода и фактическим результатом.
Если все слоты исчерпаны, раунд завершается как недоступный с сохранённой причиной;
новой попытки в том же раунде нет.

В `round.json` версии 2 каждая завершившаяся попытка содержит `diagnostic`:
категорию результата, допустимый HTTP-статус и известный код ошибки, признаки
тайм-аута, превышения размера вывода, наличия stderr и наличия/валидности отчёта.
`reason` по-прежнему описывает основание запуска резерва; `diagnostic` описывает
результат самой попытки, поэтому причина отказа Sol не подменяется причиной отказа Spark.
При исключении запуска сохраняются категория `execution_failed` и известный код ОС;
резерв остаётся использованным даже при неизвестном исходе запуска.
Завершение процесса по сигналу обозначается `signal_termination`; сам сигнал
сохраняется в записи попытки и не доказывает отмену пользователем. Статус раунда
`cancelled` устанавливается только при срабатывании его `AbortSignal`.

Аудит содержит фиксированные категории и разрешённые коды, без исходных сообщений
провайдера, stderr, токенов или содержимого входа. Категория `process_failed` означает,
что причина не распознана; код завершения сам по себе не устанавливает первопричину.
Из stderr распознаются только известные ошибки аргументов/конфигурации CLI и сертификата,
если структурированного события ошибки нет. Эта диагностика не разрешает новые попытки
и не меняет правила запуска резерва. Общий предел stdout и stderr остаётся 2 МиБ;
после превышения предела оставшийся вывод отбрасывается без повторной отправки сигнала.
# Дополнительная независимая роль DeepSeek

Общий профиль Flash / max для C2 и C3, способы включения, границы доступа и
порядок обработки результатов описаны в [DEEPSEEK.md](DEEPSEEK.md). Основная
пара и утверждённый резерв Codex сохраняются. Третья роль включается явно;
её отсутствие не добавляет обязательный gate, полученные замечания разбираются.
